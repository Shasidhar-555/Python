STAGE 3: CRITICAL DESIGN DECISIONS
================================================================================
• Deduplication Engine:
  In-memory Python set() utilizing SipHash/MurmurHash for O(1) expected time lookup per student, avoiding catastrophic O(N^2) list searches.

• Email Validation:
  Strict string methods (count('@') == 1, split('@'), split('.'), isalpha() for TLD) guaranteeing zero ReDoS (Regular Expression Denial of Service) vulnerability.

• Error Confinement:
  Granular try-except blocks: File I/O handled at file level; line parsing handled at line level. A malformed line skips only that line.

• Stream Processing:
  Line-by-line generator iteration ensures minimal working set memory footprint even if department files hold 100,000+ records.

ALTERNATIVE CONCEPT & COMPLEXITY ANALYSIS: O(N) SET VS O(N^2) LIST DEDUPLICATION
================================================================================
Mathematical Complexity Comparison:
  1. Set-based Deduplication (Implemented Solution):
     - Hash lookup: Average O(1) time per student registration.
     - Total Time for N registrations: O(N) linear time.
     - Space Complexity: O(N) hash table memory (~4x-8x pointer overhead).
  2. List-based Deduplication (Alternative Solution):
     - Linear scan: O(k) comparisons for the k-th student (searching seen_list).
     - Total Time for N registrations: Sum(k=1 to N) k = N*(N-1)/2 = O(N^2) quadratic time.
     - Space Complexity: O(N) flat array memory.
