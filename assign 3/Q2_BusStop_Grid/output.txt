PART 2: HASHABILITY EXPERIMENT - LIST AS DICTIONARY KEY
========================================================================================
Attempting to insert key of type <class 'list'>: [13.0418, 80.2341] into a dictionary...
CAUGHT EXPECTED ERROR: TypeError: cannot use 'list' as a dict key (unhashable type: 'list')

EXPLANATION:
1. Python dictionaries are implemented as open-address hash tables.
2. A dictionary key must implement `__hash__()` and satisfy the invariant that
   its hash value never changes throughout its lifetime.
3. Lists are mutable (elements can be appended, removed, or reassigned in-place).
   If a list could be hashed, mutating the list would change its hash value,
   meaning the key would now be located in the wrong hash bucket, making lookup
   impossible and corrupting hash table integrity.
4. Therefore, lists deliberately set `__hash__ = None` in CPython, raising TypeError.
5. Tuples containing only immutable elements are hashable and guarantee immutable integrity.

1. Aliasing (aliased_grid = original_grid):
   aliased_grid is original_grid : True

2. Shallow Copy (shallow_grid = copy.copy(original_grid)):
   shallow_grid is original_grid         : False (Outer list is NEW)
   shallow_grid[0] is original_grid[0]   : True (Inner row lists are SHARED!)
   Appended row to shallow copy -> len(original): 2, len(shallow): 3
   Modified nested element shallow_grid[0][1] = 777:
   original_grid[0][1] is now            : 777 (Shared reference updated!)

3. Deep Copy (deep_grid = copy.deepcopy(original_grid)):
   deep_grid is original_grid           : False (Outer list is NEW)
   deep_grid[0] is original_grid[0]     : False (Inner row lists are NEW!)

CONCLUSION: WHEN TO USE TUPLE VS LIST & IMMUTABILITY PROTECTION
========================================================================================

1. WHEN TO USE A TUPLE:
   - For heterogeneous fixed records (e.g. coordinates (lat, lon), database rows, RGB colors).
   - Whenever an object must serve as a dictionary key or set element (demands hashability).
   - When communicating data across functions that must NEVER be modified in-place by callers.
   - For read-only data structures where memory efficiency and immutability guarantees matter.

2. WHAT IMMUTABILITY PROTECTS YOU FROM:
   - Accidental Side Effects: Prevents helper functions or background threads from silently
     modifying shared state.
   - Hash Table Invariant Corruption: Ensures dictionary and set keys maintain constant hash
     values and bucket assignments throughout program execution.
   - Aliasing Bugs: Eliminates bugs where two variables referencing the same sequence cause
     unintended synchronized mutations (as demonstrated in the `[[0]*cols]*rows` bug).
